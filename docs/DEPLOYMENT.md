# Deployment: Render + Upstash + Vercel

| Part | Where | How |
|---|---|---|
| API (Docker) | Render web service, free plan, Singapore | `render.yaml` Blueprint |
| PostgreSQL 16 | Render PostgreSQL, free plan, Singapore | `render.yaml` Blueprint (not reachable from the internet) |
| Redis (cache) | Upstash, free plan | created by hand; host and password go into Render |
| Storefront | Vercel (existing project) | `REACT_APP_API_URL` points at the Render API |

Render deploys from the branch `upgrade/production-ready`. `main` (and the old Railway deployment that builds from it) stays untouched until the upgrade is merged.

## Free-tier limits to know

- **Cold start.** A free Render web service sleeps after 15 minutes without traffic, and the next request waits for the app to start. In a local rehearsal with the same limits (Docker `--cpus 0.1 --memory 512m`), the API started in **122 s** with the JVM flags in `render.yaml` (C1-only JIT, serial GC). With default flags it took 305 s. The first deploy also seeds 499 products, which adds about 2 minutes once. To avoid cold starts, point a free uptime monitor (UptimeRobot, cron-job.org) at `https://<api>/actuator/health` every 10 minutes. 750 free instance hours a month cover one service running all the time.
- **Memory.** Peak in the rehearsal was 320 MB of 512 MB, with no restarts or out-of-memory kills after the smoke test and load.
- **CPU.** 0.1 CPU is slow: in the rehearsal even cached catalog requests took about 400 ms (p50). Real latency on Render is measured after deploying (see the end of this file).
- **Database expiry.** Render's free PostgreSQL databases expire after a fixed period (30 days when this was written; check Render's pricing page). Before then, upgrade the database or recreate it; Flyway rebuilds the schema and the catalog is re-seeded.
- **Upstash free plan** has a monthly command limit. If it is exceeded, cache calls fail and the API falls back to the database (it keeps working, just uncached).
- **Email.** No SMTP server is configured (`MAIL_ENABLED=false`), so order confirmations are written to the log instead of being sent.
- **Background jobs** (order expiry, email retries) only run while the instance is awake. They catch up when it wakes.

## Steps

### 1. Razorpay: new test keys
The old test key and secret are in this repo's git history, so create new ones: Razorpay Dashboard → **Test mode** → Account & Settings → API Keys → regenerate. Keep the Key ID and Key Secret for step 3. Stay in test mode.

### 2. Upstash: Redis database
console.upstash.com → **Create database**: Redis, free plan, region **AWS ap-southeast-1 (Singapore)** (next to the Render region), TLS on (the default).
From the database page, copy:
- **Endpoint** (host, without `https://` or a port), for `REDIS_HOST`
- **Password**, for `REDIS_PASSWORD`

### 3. Render: Blueprint
dashboard.render.com → **New** → **Blueprint** → connect the GitHub repo `ecommerce-server`, branch **`upgrade/production-ready`**. Render reads `render.yaml` and asks for these values:

| Variable | Value |
|---|---|
| `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET` | from step 1 |
| `REDIS_HOST`, `REDIS_PASSWORD` | from step 2 |
| `CORS_ALLOWED_ORIGINS` | the storefront URL(s), comma-separated, no trailing slash. For now the Vercel preview URL of the branch (step 4), e.g. `https://<project>-git-upgrade-production-ready-<you>.vercel.app` |
| `FRONTEND_URL` | the same storefront URL (Razorpay sends shoppers back there) |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | your real admin login (keep it private; password 8+ characters) |
| `DEMO_SHOPPER_EMAIL`, `DEMO_SHOPPER_PASSWORD` | public demo shopper for reviewers, e.g. `demo@bazaarly.app` |
| `DEMO_ADMIN_EMAIL`, `DEMO_ADMIN_PASSWORD` | public **read-only** admin, e.g. `demo-admin@bazaarly.app` |

`JWT_SECRET` is generated by Render, and the database settings are wired from the Blueprint. **Apply**. The first deploy builds the image, runs the Flyway migrations, seeds the catalog and creates the accounts. Then `https://<api>/actuator/health` returns `{"status":"UP"}`.

### 4. Vercel: point the storefront at the API
The push of `upgrade/production-ready` already created a **preview deployment** of the storefront. In the Vercel project → Settings → Environment Variables, add:
- `REACT_APP_API_URL` = `https://<api>.onrender.com`, for the **Preview** environment (production keeps the old API until the merge)

Then **redeploy** the branch's preview: Create React App reads the variable at build time. The stable preview URL is the branch alias shown on the deployment (`...-git-upgrade-production-ready-...vercel.app`). Make sure it matches `CORS_ALLOWED_ORIGINS` in Render.

### 5. Optional: keep it awake
Create an uptime monitor on `https://<api>/actuator/health` every 10 minutes.

### 6. After the live checks pass: go to production
1. On Railway, pause the old service or turn off auto-deploy, so merging to `main` does not redeploy the old setup there.
2. Merge `upgrade/production-ready` into `main` in both repos.
3. Render: set the service's branch to `main` (and in `render.yaml`).
4. Vercel: set `REACT_APP_API_URL` for **Production** as well, and redeploy production.
5. Render: add the production storefront URL to `CORS_ALLOWED_ORIGINS` and set `FRONTEND_URL` to it.

## Live verification

Checked on the live deployment (Render Singapore, Upstash, Vercel preview), November 2026:

- **Health:** `/actuator/health` returns `UP`. Other actuator endpoints (e.g. `/actuator/env`) are not exposed.
- **CORS:** requests from the Vercel preview origin are allowed.
- **Catalog:** 499 products seeded; listing, filters and search work.
- **Roles:** the demo shopper (`ROLE_USER`) gets 403 on admin endpoints. The demo admin (`ROLE_ADMIN_VIEWER`) can read the admin panel but gets 403 on every write.
- **API docs:** Swagger UI lists 30 paths.
- **Checkout with a real test-mode payment:** order placed with stock reserved; Razorpay payment link paid (Netbanking test bank); the order became `PLACED` with payment `COMPLETED`, the cart line was removed, and the stock stayed reserved. A second payment request for the same order returns the same link.
  - This found a bug the tests had missed: Razorpay creates no order ID for a payment link until it is paid, so matching payments by order ID rejected every real payment. Payments are now matched through the stored payment link (commit `5368763`), with a regression test that models Razorpay's real behaviour.
- **Latency** (warm instance, from India): about 250–265 ms p50 for catalog requests, mostly TLS and Render's proxy.
- **Cold start:** not measured yet.
